# Reserved request catalog revalidation

This recovery path preserves an existing unsubmitted reservation when catalog evidence expires. It creates no new reservation or descendant, never resets a queue and never releases a hold. Code implementation and offline validation do not authorize live admission, private capture or provider requests.

## Why refresh alone cannot resume

A fresh catalog snapshot has a new identity that participates in compilation. Byte-identical synthesis can acquire a different request revision. Ordinary envelope/spend equality remains strict. A separately reviewed mapping binds the immutable original envelope to the exact fresh compilation. Revision normalization is used only to classify rejected comparisons, never to construct an executable envelope.

Fixed capture/admission diagnostics distinguish source, payload, envelope, revision, selected catalog binding, pin, expiry, build/profile and retained-evidence failures. They preserve relevant expiry metadata without raw exception prose, credentials or article content. Logging failure cannot manufacture authority or disrupt ordinary library readback.

## Private review before admission

In **Internal article narration**, select the held coverage and use **Prepare private catalog-resume review (no reservation)**. Select its retained historical article-admission JSON and a NEW physical local destination. Existing or partial files are never overwritten. Network paths, links and reparse-point directories are refused using the shared managed physical-directory policy. This is best-effort path validation, not protection against an attacker replacing directories concurrently.

The application verifies actual source/revision, retained reservation, original policy hash, financial history and current account/project/catalog/pricing context, then uses the ordinary trusted compiler. The private JSON contains binding/financial/history metadata and possibly local audio paths, but no article text, audio or credentials. Keep it private. It has no source approval or installer pin and explicitly grants no authority. A preview hash, checkbox or remembered voice cannot admit it.

The older `InspectReservedCatalogCandidateAsync` inspection API also remains non-authoritative: its catalog fields are explicitly unauthenticated and its digest is not the approved financial baseline. It is not an execution mapping.

## Independently admitted scope

Review the private candidate against actual bounded user approval and current evidence. Current resume policy separately pins the reviewed App/Infrastructure hashes and existing profile; original policy, authorization, immutable attempt/envelope, clean queue and approved financial digest; exact current selection, full fresh compilation identity and runtime trust; unchanged source/payload/voice/options/account/project/credential/pricing; fresh authenticated catalog; fresh approval and expiry; one existing dispatch, ZERO new reservations and ZERO additional reservation.

Historical validity is checked at the actual original reservation time, never as current spending authority. Original expiry is unchanged. The stored original envelope and full payload hash remain intact; full fresh compilation identity is additionally retained. A short revision hash alone is insufficient proof.

Use the normal installer with separately reviewed `-ReviewedChirpResumePolicyPath` and `-ReviewedChirpResumePolicySha256`, matching clean build and inspected existing profile. Normal closure, backup, rollback and build/profile checks apply. Resume admission cannot be combined with new-reservation authority or profile migration. Ordinary updates never silently copy/re-admit private authority. Arbitrary runtime JSON cannot install its own pin.

## Revalidate, then act separately

Review the held request and acknowledge **Revalidate SAME held request (no new reservation)**. Fresh compile and selection are rechecked. Capture time is excluded from stable identity but separately checked for freshness. The transaction appends only the admitted mapping. Identical replay/resume returns the same authorization/key and held amount.

Private capture remains separately approved, explicit, default-off, one-response and independently time-bounded. Generate is a separate explicit action. Review/mapping never sends synthesis.

Before dispatch, the shared resolver rechecks authority, exact mapping head, authenticated evidence, original financial/source state and clean queue. One immediate transaction inserts a unique dispatch mapping, consumes the SAME authorization and sets the durable queue uncertainty barrier. Root/successor and queue database guards block legacy clients from claiming mapped reservations without the exact binding. Failure, cancellation or revocation rolls back all three changes. Orphan bindings require reconciliation and confer no retry/cleanup authority.

No mapping or paid replay is allowed after dispatch or uncertainty. Failures retain holds. Accepted journals/receipts identify the mapping actually bound to dispatch. Local recovery/export verifies that historical mapping after expiry and reuses accepted bytes rather than regenerating them.

## Expiry before submission

If still unsubmitted, a later explicitly approved scope can supersede expired evidence. It must name the exact predecessor/head and use a distinct fresh approval; there is no automatic renewal. The bounded canonical append-only chain permits one root and one child per predecessor, with no forks/orphans/cycles or timestamp-based head choice. Original authorization, policy, envelope, financial digest and held amount are unchanged. Only the independently admitted current leaf can execute, once per original authorization.

## Validation and delivery limits

Synthetic coverage includes mismatch/expiry, malformed or unpinned authority, build/profile, restart/replay, root duplication, approval reuse, supersession, concurrent mapping/claim, interrupted transactions, orphan state, actual legacy SQL claims, logger failure/redaction and accepted-output recovery. The additive migration preserves prior business rows and creates empty audit tables only. Draft-save tests cover cancellation, existing/partial files and path rejection where the host permits a link fixture.

Release still requires exact-head full CI/dependency audit, final independent review, isolated native UI/picker/capture acceptance and controlled backed-up installation. Report restricted/untested operations rather than calling them passes. Live use requires fresh exact authority after delivery. Full article generation additionally requires the exact remaining manifest and reconciled budget. Historical startup-crash uncertainty and heard-audio limitations are unchanged.
