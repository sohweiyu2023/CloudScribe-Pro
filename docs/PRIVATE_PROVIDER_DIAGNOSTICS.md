# Private provider validation diagnostics

Normal logs retain HTTP status, response-read metadata and request hashes without provider-message text. Older messages discarded by those logs cannot be recovered retrospectively. A generic error category does not mean Google supplied no explanation.

Root and nested explanatory message/description/reason/domain/field strings use the same private redaction before persistence. Unknown fields and collection limits are explicitly marked as other provider details omitted. The private view shows that flag separately from byte truncation. New ordinary events distinguish pending retention from actual saved/failed retention; no private wording is copied into those events or support export. The default selected-explanation mode retains its HTTP400/INVALID_ARGUMENT scope. Protected response evidence is a separate explicit choice described below.

For an unfamiliar Google HTTP400/INVALID_ARGUMENT explanation, open **Workspace inspector → Advanced tools → Private provider error diagnostics**. This feature is off by default.

1. Save the document and select its current Google account and voice.
2. Read the privacy notice, check the explicit consent box and choose **Enable once for selected saved request**.
3. This arms diagnostics for that exact saved document, revision, account, voice and compiled request for at most ten minutes. It does not approve spending or send anything. Any generation still needs its ordinary separate authorization.
4. The first matching authorized dispatch consumes the opt-in even on success, cancellation or failure. Changing the selection/text, disabling capture or closing the app cancels pending opt-in. It is never restored automatically after restart.
5. After an independently authorized request, reopen the private view and choose **Read private local records**. The read-only text cannot execute links, markup, approvals or retries. Check whether saving succeeded; a pending or failed private write does not establish retention.

In selected-explanation mode, only the bounded parsed validation message is eligible. Missing, ambiguous, invalid, oversized or other-category responses retain fixed status metadata instead. Unknown wording is preserved after redaction; it need not match a known-message classifier. HTTP outcomes, reservations and reconciliation rules are unchanged.

Known access-token forms, credential-shaped values and full-input echoes are removed before truncation. Known contiguous input fragments of at least eight Unicode scalars, Unicode-normalized/newline-normalized forms and supported JSON/URL/base64 forms are also suppressed. This cannot guarantee anonymity for arbitrary transformed, very short or unrelated personal data. Remaining text is always **PRIVATE**.

At most eight records are retained. Selected-explanation records are at most4KiB including JSON and at most2KiB UTF8 message text. Records expire after24hours and are removed on the next store access; interrupted temporary records are cleaned on access. The view marks truncation. A single bounded persistence worker receives already-redacted records only, with no credential/request context. Slow or failing storage never delays the known provider outcome. Orderly disposal allows at most250ms for pending persistence; immediate process exit or failed storage can still lose a private record. Readback is required to verify retention. Physical deletion while the app is closed is not guaranteed.

## Protected response evidence (separate consent, off by default)

The private modal offers a separate protected-response choice. Changing that choice clears consent and disarms capture. It never approves a request or grants spending authority. The exact saved request, version, account, project, voice, credential reference and compiled payload remain bound to one response for at most ten minutes. No opt-in is restored after restart.

This mode retains bounded redacted error evidence across HTTP statuses, including nested unknown explanatory fields, empty/malformed responses and incomplete reads. Safe status, parse/read state, omission, redaction and truncation flags accompany the private body. Known credentials and input echoes are masked; audio fields, numeric arrays and ambiguous encoded content are omitted. False-positive omission is possible, including encoded-looking reason strings; canonical provider status is retained separately. An arbitrary provider response cannot be guaranteed anonymous or complete after masking. Success audio is never deliberately captured; success retains metadata only. A timeout, missing body or expired diagnostic never proves that a request was not submitted, and cannot release a spending hold or authorize a retry.

At most16KiB of body evidence is inspected/retained; escaped JSON can require further reduction. The decrypted envelope is bounded to32KiB, the Windows current-user protected file to64KiB, and the shared store to eight records. Protection has no plaintext or machine-scope fallback. Preflight checks existing records and a protected synthetic write/read before arming. Later storage failure is still possible and must remain visible; it does not change the provider outcome or trigger a replay.

Legacy selected-explanation records are unencrypted and inherit their folder's permissions. Protected records use the current Windows user's data protection without changing those permissions. This does not protect against administrators, impersonation or code already running as that user. Both kinds remain private and excluded from routine logs, support bundles and release packages. Header request IDs remain hash-only routine evidence, not a recoverable support lookup ID. Logical24-hour expiry and cleanup on access apply; external copies and backups are not automatically erased.

Sentence-plan diagnostic successors require their own typed schema4 purpose, full unchanged proposal and failed-parent lineage, exact one-attempt/one-cent grant and separate protected-response consent. They cannot authorize a whole-article job. The matching completion workflow must independently admit that purpose and installed build, preserve all historical counters/holds, and reject duplicate or uncertain execution. An available implementation is not live authority: no evidence collection may occur without its precise reviewed authorization and platform checks.

The private store is a sibling of the exact configured profile, under `.cloudscribe-private-diagnostics/<profile-hash>`. An isolated QA profile keeps its private store in that same isolated parent; there is no fallback to the real user profile. This location is outside the existing profile/Generated backup roots and normal support-export roots. Normal diagnostics exports, telemetry, Git/source packages and sharing packages must never include these private records. An explicit external copy or OS/user backup may outlive the active-store retention period; old backups are not automatically purged.

This setting does not clear failed-attempt holds, change budgets, authorize a paid test or diagnose messages that were never retained. Keep failed reservations until actual billing is reconciled, and stop after any specifically authorized bounded test.

## Diagnostic successors for consumed article requests

A consumed article request cannot be submitted again. A separately reviewed diagnostic admission can authorize one new successor only for an exact, resolved HTTP400/INVALID_ARGUMENT failure with no accepted output. It retains the original attempt, reservation and receipt history. Accepted or uncertain requests are ineligible. The grant binds the failed attempt, unchanged compiled bytes, source revision, voice, account, credential reference and current installed build; it allows at most one new request and one additional cent. Ordinary project headroom does not renew that authority.

Prepare and explicitly approve the displayed successor reservation, then enable private capture for that exact active request. The application requires the attached, unexpired one-response ticket before consuming the database dispatch claim, and checks it again after credential resolution before HTTP dispatch. An opt-in for another request object is insufficient. Restart, expiry or withdrawal never rearms capture automatically. Withdrawal after a durable claim can leave an uncertainty barrier even when local evidence shows no HTTP dispatch; the application retains that barrier and reservation rather than silently retrying.

Capture readiness is a dispatch safeguard, not a guarantee that a late response or failed disk write will retain its message. Inspect the current attempt, capture status and private readback after the single outcome. Any further diagnostic attempt requires a new independent bounded admission; neither the error text nor a prior exhausted grant supplies permission.

A typed diagnostic transition preserves the original window when it is still valid. After a terminal predecessor expires, a distinct explicitly approved transition may instead authorize one fixed ten-minute evidence window. It requires fresh clock evidence and approval, retains the predecessor history and actual used refresh/admission counters, and cannot renew itself or authorize batch generation. Missing approval, pending/uncertain work, replay or a changed request remains blocked.
