# Supervised completion run gate

This optional private gate restricts an independently approved narration run. It does not grant Google access, approve spending, create credentials, release holds or replace the existing per-request financial, identity, queue and uncertainty guards. Ordinary installations without a gate requirement keep their existing behavior. A required gate that is missing, corrupt, expired or uncertain fails closed.

## Delivery and activation

Use two phases. First build/review/test the hook-capable release, install it normally without live authority, and verify the actual installed App/Infrastructure hashes and protocol1 installation marker. Preserve documents, accepted audio, financial rows and rollback. Do not activate a scope while upgrading an older ungated binary: an interruption could otherwise leave that binary unaware of the requirement.

After actual readiness and matching user approval, independently review the exact private gate configuration, immutable six-hour UTC scope and hash-only article manifest. Scope `plansSha256` is the canonical sorted-JSON SHA256 of the manifest, not merely an article title. Manifest proposal hashes bind original document/revision/source/cutoff, language, voice, ranges and all compiled payloads. Its permitted parts include the one existing held part and only the untouched new parts; accepted coverage is excluded. Check payload/bytes/voice matches are unique before admission; ambiguous repeated payloads are conservatively rejected, not regenerated or normalized.

Freeze the reviewed `gate_cli.py` and `completion_register.py` bytes in a private fixed helper directory. Pin those files and the existing Python executable in the private configuration; the helper launches with `-I -S` and explicitly loads only the hash-verified module source. Do not include user configuration, scope, approval records, register, anchor or audio in source publication, support export or a clean release ZIP.

The reviewed initializer is `tools/completion_workflow/initialize_reviewed_register.py`. Supply separately reviewed gate/scope/approval files and hashes through its documented arguments. The initializer checks the already-installed hook build and profile, creates the register exactly once and grants NO spending authority or app activation. Concrete six-hour start/end timestamps are fixed before initialization, after readiness; the window is not silently extended if preparation consumes time. Existing/corrupt/partially initialized registers are never overwritten or reset.

Activate through `Install-CloudScribe.ps1 -ReviewedCompletionGatePath ... -ReviewedCompletionGateSha256 ...` using the exact same already-installed package. The installer persists an independent profile required marker before activation, pins the private gate in the install marker and retains rollback. Partial activation remains blocked. Existing active gates cannot be dropped through ordinary update/migration or replaced with a fresh counter. Stopped/expired gates and any later retirement/new run require independently reviewed reconciliation; do not delete markers, restore old journals or fall back to an ungated binary to continue a run.

## Repairing a build during the same run

A reviewed diagnostic repair may use `-ReviewedCompletionBuildTransitionPath` and `-ReviewedCompletionBuildTransitionSha256` with the independently reviewed successor gate. This permits one build transition before any resume or completion-policy admission, with no pending operation. The transition binds both builds and gate configurations, the original approval and scope, and the exact clean journal head. Account, credential reference, profile, plans, interpreter, deadline and counters cannot change. It grants no financial or provider authority.

The installer durably claims the transition before changing files, rechecks closure and staged hashes before swapping binaries, atomically advances the profile requirement, then verifies actual installed files and pins before completing the journal event. Interruption leaves normal operations blocked. Do not rerun installation blindly or reset a marker: reconcile actual files first. Only the same pending transition can complete through its verified readback path; expiry still stops it. The previous build, source and configuration remain available for evidence and rollback, but an old client cannot continue the active run after succession.

Resume evidence compares validated HTTPS root origins canonically, so an authority with and without its trailing slash represents the same origin. Different hosts, nondefault ports, credentials, paths, queries and fragments remain rejected; endpoint, account and request identities retain their exact checks.

## Enforced operations and evidence

Production bootstrap owns a durable operation before credential/token/network access. The Create MP3 auto-loader owns the entire cycle, including the second authenticated catalog GET used for UI population. The cycle permits at most two catalog GET stages and one exact input-free `{}` synthesis capability probe. Direct catalog/probe calls outside a live owned cycle and credential repair/fresh configuration during the run are rejected. No alternative synthesis engine exists.

Catalog success requires the intended exact voice/language to be present. The empty probe expects HTTP400 plus parsed canonical `INVALID_ARGUMENT` and no audio; other statuses, malformed/missing evidence or unexpected audio fail. Real observed catalog/probe data plus verified persisted evidence produce the receipt; UI/caller booleans are not authority. Leases are sealed, correlated, synchronized and revoked on close. In-flight or inconsistent second responses cannot be hidden by successful completion. Subprocess source/pins and actual pending ticket/deadline are rechecked before effects; timeouts are uncertain, never automatic retries.

When reopening a UI after a resume admission, authenticated catalog/probe verification still runs and is counted. If the independently admitted snapshot is still current/unexpired AND both new observations reproduce its exact combined provenance and the admitted envelope provenance, bootstrap retains its exact identity and OLD expiry instead of silently invalidating the admitted request by writing a new GUID. No lifetime is extended. Changed catalog/probe provenance or expired evidence receives a new snapshot and requires explicit reviewed revalidation; a missing intended voice fails. Changed selection/provider/runtime evidence still fails the existing exact compilation guards.

Resume-policy installation claims a separate durable ordinal and permits zero new reservations/funds. It validates exact proposal/coverage/payload/voice and original held identity before installation, rechecks expiry before swap and verifies actual installed pins afterward. A subsequent resume can retain the SAME previously admitted completion-policy bytes only if the register proves their earlier successful admission; it cannot renew or reset budget, attempts or expiry. The one completion-policy admission must exactly match the approved remaining coverage and at most108 new attempts/108 cents, USD cents, inside the reviewed project cap. All ordinary policy/financial validators still run.

There are at most24 logical catalog/bootstrap operations,24 resume admissions and one remaining-completion policy admission. Logical refreshes include their token acquisition, catalog retrieval and expected input-free capability request; they are not24 individual HTTP calls. Attempts are counted before effects, including failures. A pending operation blocks concurrency and restart until genuine observed reconciliation; no slot refund/reset is provided. Provider dispatch remains the existing one-request-at-a-time approved path. Its uncertainty/receipt/financial guards remain mandatory, and the supervising workflow must stop on the first synthesis/delivery failure rather than dispatching another part.

## Durability and clocks

The private register uses SQLite FULL synchronization, an exclusive cross-process lease, immutable hash-chained events and a separately fsynced append-only sequence/head anchor. Missing/denied/corrupt storage, interrupted writes, database/anchor divergence, replay and scope/path changes fail closed. Status/pre-effect checks persist UTC and monotonic high-water marks. The fixed deadline is bounded by both UTC and elapsed monotonic time; rollback or discontinuity stops the run. A reboot or clock discontinuity requires reconciliation, not an automatic new window. Small clock-read skew does not extend the monotonic deadline.

Journal size/event bounds are finite. Exhaustion fails closed. Deliberate restoration/deletion of ALL independent scope/journal/anchor artifacts by a filesystem owner cannot be made tamper-proof by a local helper and is not claimed. Loss or uncertainty requires independent reconciliation. No registry, antivirus, operating-system clock/security or remote telemetry settings are changed.

Private capture remains default-off, exact-request, explicit opt-in, one response/ten minutes with existing24-hour private retention. Arming and resume approval also require a ready global run. Disabling capture, reading retained private diagnostics and local receipt/output recovery remain possible without renewing paid authority. Local assembly/export after accepted coverage does not require a fresh catalog or provider call.
