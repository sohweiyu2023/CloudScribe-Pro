# Reviewed narration recovery integration

The backend and integration implement historical import, independently admitted evidence/budget stores, explicit additional-attempt review and dedicated recovery claims through the existing production runtime. Availability remains conditional on an exact-build, exact-profile independently reviewed private policy; none is included or automatically admitted. No failed request is auto-retried and no historical audio is auto-imported. No selected JSON file, caller-supplied budget number or computed file hash is an authority source.

## Installer-admitted historical evidence

The optional private policy is bound to the exact App and Infrastructure DLL hashes, canonical profile identity, account/project, expiry and independently reviewed evidence. Runtime loading accepts only a bounded, strictly parsed policy whose hash was separately admitted in the install marker. It rechecks authority on each operation. An ordinary UI user can select only an admitted evidence ID, then verify the original request and retained MP3; the UI cannot admit policy files or change their pins. Confirmed import remains a local provenance operation with no provider or financial action. The article dialog refreshes completeness after the review closes.

This pin uses the existing normal-user installer/binary trust boundary. It is not protection against an actor who can replace both installed binaries and their marker. No new credentials, signing keys, persistent permissions or security settings are introduced. A policy is private and excluded from clean/public packages. No policy is supplied by this source update. Ordinary updates do not copy or silently re-admit an old policy; its prior bytes remain only with the retained rollback installation.

Optional installer policy admission requires PowerShell 7 running on .NET 8 or later, and fails before writes if that capability is absent. Ordinary policy-absent updates retain their Windows PowerShell path. Both a separately reviewed policy file and its independently approved SHA256 must be provided; computing a selected file's hash alone is not approval. Admission checks nested schema/types, duplicate properties, scope, financial pin bounds and exact build/profile identity before staging. Runtime checks the same policy again. Real evidence admission, live import and native acceptance remain separate controlled gates.

Schema 2 also requires explicit `MaximumNewAttempts` and `MaximumAdditionalReservationMinorUnits` on each independently admitted predecessor grant. These are immutable per-admission limits, separate from the continuing project/allocation ceilings. Every reserved child counts, including failed, consumed and uncertain attempts; no outcome refunds the grant. A one-attempt, three-cent grant therefore cannot authorize a descendant or a larger reservation. An interrupted transaction consumes nothing; restart may activate the same existing reservation without consuming another attempt. Historical zero-cost audio import has its own evidence scope and consumes neither paid-attempt allowance nor financial reservation. Schema 1 and missing limits fail closed. The additive database migration preserves legacy fields and holds, leaves their new limit fields null and blocks legacy execution until separately reviewed bounded authority exists.

## Historical accepted audio

`ArticleAudioExportService.PrepareHistoricalImportAsync` accepts an already-admitted evidence ID, exact original compiled request and original local audio path. An injected `IReviewedHistoricalAudioAnchorStore` must independently resolve immutable acceptance-time evidence and its admitted digest. Without that store, the path fails closed. A store implementation must independently establish acceptance provenance; it must never accept a file's self-declared digest or ordinary caller-selected metadata as admission.

The service verifies full account/operation/request/local-attempt identity against durable accepted queue state; exact payload hash and length, plain text, voice, language and MP3 encoding; current document/revision/text, original parent revision and exact ordered group; and the original audio's hash/length. It rejects missing, uncertain, mismatched, duplicated or changed evidence and linked paths. It copies input memory and returns a bounded, short-lived opaque review. No provider response is reconstructed.

Import requires fresh confirmation of that exact review digest. The service resolves the admitted anchor again and repeats all current state/file checks before atomic no-overwrite receipt publication. New receipt fields distinguish historical evidence and admitted anchor digests. Exact repeated reviewed import is idempotent; conflicting existing evidence fails. Cancellation or failed validation does not publish a receipt. The original audio and financial/queue records stay unchanged. Future export still verifies current provenance and audio snapshots before publication.

Accepted queue flags alone do not prove audio identity: older queue records contain no audio hash. If no sufficient contemporaneous anchor survives, preserve the old audio as unverified local output. Do not regenerate it to repair presentation, infer association from filenames, or fabricate a provider ID/accepted response.

## Additional billable attempt with historical holds retained

`GoogleExplicitRecoveryService` has no provider or credential dependency. Preparation uses exact saved document/revision/plain-text bytes and a compiled envelope. It requires trusted composition-owned `IGoogleRecoveryBudgetEvidenceResolver` and `IGoogleRecoveryPredecessorEvidenceResolver` dependencies. The production composition supplies the installer-pinned admission store and `InstalledRecoveryBudgetEvidenceResolver`, with no permissive fallback. Ordinary preparation callers supply neither budget truth nor predecessor authority.

The budget authority must derive current conservative commitments, every uncertain historical hold, approved project/allocation ceilings and remaining allocation from independently admitted durable evidence. It must bind its result to the exact account/project/currency/scale, current financial-state digest and expiry. It must include this service's durable additional reservations in subsequent totals. A resolver that merely echoes caller numbers or an arbitrary hexadecimal string violates the contract.

The concrete resolver requires exact pinned baseline queue, spend-authorization and recovery rows plus independently reviewed conservative totals. It reads a bounded coherent deferred SQLite snapshot and checks the exact current financial digest. All additional recovery reservations count in full, including consumed, failed, accepted or uncertain attempts; no outcome frees a reservation. Every extra queue identity must exactly match a valid durable recovery authorization/link, retained amount, admitted narration root and owned claim/outcome. A matching row count or key prefix alone is insufficient. Missing/mutated baseline rows, foreign spend or unaccounted queue activity fail closed and require independent reconciliation/review, never a budget reset. Existing retained floors and allocation limits cannot be relaxed. This conservative model can block availability after unrelated financial changes; it does not guess missing accounting evidence or the provider's final invoice.

The predecessor authority must bind the actual historical key and state digest to the logical narration item, project/document/revision/text and original payload digest. Missing legacy local-attempt or provider IDs remain missing; they are never invented. Logical identity comes from this admitted mapping and remains stable across voice/catalog rotations. Descendants retain the same root evidence identity. Review digest, durable approval and claim all bind its admission digest; revocation, replacement or expiry before claim blocks dispatch.

Preparation creates no executable child identity. Fresh explicit confirmation must authorize the displayed additional ceiling and acknowledge that old uncertain attempts may still be charged. In one SQLite transaction approval appends immutable recovery/link evidence, creates one clean child queue row, and increases the retained reservation floor while decreasing remaining allocation. It never replaces an old spend authorization, old queue row, attempt identity or hold. A later scope cannot lower retained commitments or expand an existing ceiling/allocation. Such amendments require a separately designed and reviewed policy.

Only one approved child may be pending per account/project; later attempts must extend the latest logical chain. A lost approval acknowledgement can be reconciled with `FindApprovedAsync` using its exact review digest; it must never be answered by minting another child. Interrupted approvals roll back together; committed reservations are retained.

The Studio's additional-attempt dialog compiles the current saved selection using composition-owned current account, credential availability, authenticated catalog, project/model, pricing, trust and post-compile checks. This read-only preview does not initialize an ordinary queue key or publish a generic pending spend approval. The user enters a bounded maximum and explicitly acknowledges retained historical holds. Request changes invalidate review. Approval appends the dedicated reservation, activates its exact durable recovery ID and clean child snapshot, and does not generate audio. Generation remains a separate explicit action through the existing command.

After restart or a lost activation acknowledgement, an unconsumed reservation can be reviewed and activated again using the same ID, child key and reserved maximum. The dialog discloses that the additional reservation is zero. A fresh resume digest binds the original approval identity, current compiled envelope/document/root, financial state, conservative budget and admitted policy. Confirmation reloads and compares those exact facts. Changed evidence requires a fresh review of the same retained reservation; it never creates another child to escape a pending reservation. Discarding an unapproved in-memory preview only frees its review slot, never durable authority or holds.

The reserved `recovery-google-tts:` namespace is rejected by the ordinary queue claim and runtime envelopes without a matching recovery ID. Generic spend persistence rejects recovery envelopes; exact-ID loads use the dedicated durable record with no fallback to an old generic approval. The recovery ID survives envelope revalidation. `TryClaimAuthorizedAsync` runs as the owned-claim callback of the existing production bound queue, **after** current admission/trust/account/credential/capability/pricing/project/model/post-compile checks. It compares full authorization/key/project/envelope/estimate, current document and financial evidence, revalidates budget and predecessor authority, and atomically consumes approval plus establishes the child's durable uncertainty barrier. At most one concurrent caller owns dispatch. Ordinary approved envelope reuse, stale price/capability evidence, changed text and consumed/replayed approval cannot substitute for this claim.

The backend and review/approval services do not construct a transport, submit a request, resolve a historical charge, release a reservation or decide that an HTTP failure was free. Only the existing production runtime constructs its usual transport; its owned claim must succeed before dispatch, and its usual outcome path records the result. Source review and synthetic tests do not authorize an actual attempt. Exact private evidence admission, applicable financial authorization, native acceptance and controlled delivery remain separate gates before real use.

## Persistence and verification

The additive `GoogleExplicitRecovery` migration creates separate recovery scope and attempt/link tables; existing document, accepted audio, queue and authorization rows are not rewritten. Downgrade refuses to delete this financial/identity history. Keep the current installed build and profile unchanged while reviewing source; use a closed synthetic clone for any migration/native acceptance and a fresh verified backup before a future controlled update.

Tests use only synthetic documents, queues, local bytes and trusted fake dependencies. They exercise exact historical import, confirmation, idempotence, mismatch, authority revocation, cancellation and file/revision changes; additional-attempt authority, legacy-null evidence, stale financial snapshots, budget floors, no branching, concurrent claims, restart/acknowledgement loss, envelope/project/estimate drift and admission replacement/revocation. Full applicable tests, exact source review and production integration acceptance are separate gates.
