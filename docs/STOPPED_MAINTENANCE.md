# Stopped maintenance update (development only)

This uses the existing sealed register and administrative claim/readback protocol.
It creates no scope, window, financial admission, capture, credential or provider authority.
Only an already stopped, expired, unused diagnostic scope with a confirmed refresh
failure and no pending/uncertain work is eligible. Scope, counters, stop cause,
accepted evidence and last-good clock watermark remain unchanged. A separate fresh
maintenance approval is required for any real use; current work is synthetic only.

An updated UI will support local document/library/settings inspection. Narration,
catalog/bootstrap and admissions remain stopped; this is not MP3-generation readiness.
The old reader rejects new administrative history; the new pinned reader validates
it without rewriting any ancestor. Rollback restores the exact predecessor bytes
and remains blocked. Its frozen old reader may report an integrity rejection rather
than a typed stopped result; rollback does not promise a usable narration build.

## Explicit return to normal manual operation

A distinct, freshly approved release record can retire the expired diagnostic
scope after maintenance completes. This is an administrative product-mode change,
not a resumption of the failed request or permission to call a provider. The
immutable old scope, stopped reason, accepted audio, spending rows and used counters
remain preserved. No dates or consumed limits are reset.

The release changes only the installation marker's two completion-gate fields.
It preserves all financial policy pins, app/runtime files and profile override.
While the app is closed and leases are held, it verifies the complete new
inventory, appends the sealed retirement, then archives (never deletes) the profile
requirement marker. Until that sealed retirement completes, the requirement stays
present, so an interrupted replacement cannot silently enable ordinary operation.
After restart the normal application no longer binds to the retired private run.
The old diagnostic admission still fails: it requires a live diagnostic gate.

Ordinary manual generation still requires current Google connection/catalog,
pricing, native spend approval and any applicable article admission. In particular,
the existing two-article continuation needs a current plan that reuses all verified
accepted ranges and counts every retained hold. Do not reimport the complete text
as a fresh paid job, silently change the voice, retry an uncertain request, or use
this release to evade a denied dispatch. Removing the expired private-run gate does
not establish that Google will accept previously rejected input.

## Reviewed operator sequence

This is not a user-facing instruction to edit or delete gate files. No live plan is
provided in this source tree. Each real operation requires separately reviewed,
immutable plan bytes and their SHA-256, with fresh state and exact package evidence.

1. Close normally; back up the closed profile and exact current installation.
   Reconcile database, financial rows, accepted media and all pending/uncertain
   outcomes. Any mismatch, unfinished effect or changed source stops maintenance.
2. Prepare an immutable latest installation outside the live tree, preserving the
   profile override and financial policy bytes. Freeze old/new gate references,
   inventories, required-marker bytes and the seven pinned helper files together.
   Only build/helper fields may differ between gates; scope, Python trust,
   account/project, voice, manifest, register and deadlines must be identical.
3. Review the maintenance plan, then use the supported installer with
   `-ReviewedStoppedMaintenancePlanPath`, its exact
   `-ReviewedStoppedMaintenancePlanSha256`, and initially `-ValidateOnly`.
   Apply with `-StoppedMaintenancePhase update` only after explicit authorization.
   Same-plan `resume` reconciles an interrupted claim; it cannot create new authority.
   `rollback` / `resume-rollback` preserve partial installations and restore the
   retained blocked predecessor with exact readback. Never erase a failed stage.
4. For normal manual mode, prepare a separate release record binding the completed
   maintenance identity, current journal head, exact manual inventory and archive
   path. A fresh release approval is mandatory; maintenance approval is insufficient.
   Validate with `-StoppedMaintenancePhase release -ValidateOnly`, then apply that
   exact plan only when authorized. `resume-release` can finish the same interrupted
   release, never start another one. Neither path reserves money or calls Google.
5. Verify actual installed hashes, normal shortcut startup and retained audio/data.
   Local UI acceptance and paid-generation readiness must be reported separately.
   Do not present a Generate instruction before current article/budget requirements
   are established and the installation has been verified.

Never combine this installer mode with migration, admission, successor/window
activation, trust rebinding or another installer mode. Unknown filesystem bytes,
unavailable storage, replay, clock rollback or changed evidence fail closed.
