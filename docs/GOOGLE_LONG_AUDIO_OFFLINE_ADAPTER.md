# Long Audio adapter: inactive offline boundary

This is an offline implementation/test checkpoint. It is not registered in production, does not create buckets or credentials, and does not enable a UI submission path. No real Long Audio request was made. Mandarin Alnilam compatibility is unverified, and no existing usable output bucket was established. Those are live-readiness blockers, not conditions this adapter assumes away. An asynchronous API and larger document limit do not establish that the same model will accept a sentence rejected by synchronous synthesis.

Protected retention is now mandatory through `IGoogleLongAudioResponseObserver`. The concrete inactive observer binds the true exact Long Audio request object, explicit consent and an explicitly supplied already-approved capture expiry. It does not create or extend a paid window. The expiry must be future and no more than six hours away, and both UTC and monotonic elapsed checks apply. No `GenerationProviderRequest` is fabricated. Because the existing echo redactor accepts at most16KiB of compiled input, this concrete observer rejects larger proposals before a durable POST claim. A safe large-input/chunk-aware redaction strategy remains unresolved: this checkpoint does not make full-article Long Audio live-ready.

Non-success HTTP bodies are read within the metadata bound and sent to the existing private envelope redactor. Valid HTTP200 operation errors are sanitized only through the explicit optional operation-error branch; their actual HTTP200 status is preserved. That branch requires a valid canonical error object and string message. Unknown message text can remain in the protected record after known-token/input redaction; anonymity is not guaranteed. Invalid structures retain explicit omission/redaction-unavailable flags, not a raw fallback. The old redactor's default success-body exclusion remains unchanged.

The concrete observer uses the existing protected persistence contract and verifies the exact saved redacted record by private readback. Its worker receives only the already-redacted bounded record, with ExecutionContext suppressed. The save/readback wait is bounded; failure, timeout or missing readback cannot replace the already-durable provider outcome. Journal fields contain only typed read/parse/retention metadata and a private record ID. An exclusive active-response lease prevents overlapping response lifetimes through this journal. A durable observation-pending guard stops another POST while outcome/retention is unknown or incomplete, and remains sticky after storage failure. This is an operational stop, not paid authority or tamper/rollback protection. No UI arm or production store registration is supplied here.

Protected observation is attempted even when the first transport-outcome journal write fails. The unchanged original local failure carries only typed observed HTTP/retention context through `GoogleLongAudioJournalFailure`; no raw exception prose enters the journal. That failure does not prove the durable journal contains the observed outcome, and its pending stop is not cleared. Error-member detection for actual HTTP200 is independent of accepting an operation identity, so a rejected operation can still retain a properly protected explanation without being accepted or assigned a fabricated status code.

`GoogleLongAudioRequest.Create` builds a bounded plain-text proposal for one exact numeric project, location, credential reference, voice, format and attempt-bound `gs://` object. The final object basename must be exactly the attempt GUID in N format with the matching `.mp3` or `.wav` extension, preventing two distinct attempt IDs from aliasing a compound basename. It escapes JSON and hashes its owned bytes; caller copies cannot mutate the stored proposal. This local bound is conservative, not a guarantee of provider acceptance. There is no fallback voice or endpoint.

`IGoogleLongAudioAdmission` has deliberately no production implementation. Before any transport invocation, the future trusted implementation must use the existing current account/project/credential, catalog compatibility, exact payload estimate, lineage, independent explicit approval and durable spend-claim pipeline. It must also establish current Long Audio voice/format support, pricing (including applicable storage/access costs), permissions for an already existing private bucket and a fresh unoccupied output object. The Long Audio request has no object-generation precondition field; a unique local GUID alone does not prove remote nonexistence. Production integration must provide an appropriate no-overwrite ownership boundary. Proposal fields, the journal and a caller checkbox cannot establish this authority. This component does not replace the existing ledger, queue or financial reservations.

The private journal claims a unique local attempt before admission, credential resolution or POST. A missing response, cancellation, malformed/wrong-scope operation, credential error, process interruption or uncertain persistence never permits another POST for that attempt. Even a definitely local pre-send failure intentionally leaves a claim requiring separately reviewed recovery; the adapter has no reset or automatic retry. A future integration must retain reservations and expose uncertainty honestly.

Successful POST responses must contain a full operation name under the exact project/location. Persisted operation names bind subsequent `PollOnceAsync` calls to an exact GET, with no POST fallback. Resume also requires the caller's original exact request and matching digest for echo redaction; hashes cannot reconstruct its text. Each poll requires its own exact protected observer context within approved consent, and is bounded; there is no autonomous/background loop, operation listing, cancellation, deletion or automatic retry. The default transport disables redirects and cookies; an injected custom handler is trusted and must not retry, redirect, forward authorization or dispatch alternate requests. Operation metadata is bounded to16KiB/depth8; duplicate consumed structures fail closed. Only safe HTTP/RPC status numbers and retention completeness metadata are journaled; no token, raw input, provider error wording/details or response body is journaled.

`CompletedUnverified` means only that the operation reports completion without an RPC error. It is not an accepted-audio receipt, proof of GCS object identity, verified bytes, decode success or a settled charge. An independently reviewed output path must verify the exact bucket/object and immutable object generation, private access, size/hash, complete download and decode, then issue the proper accepted-output receipt before export. That path is not implemented here.

The file journal is a private single-machine persistence primitive with exclusive per-attempt leases, physical-directory/link guards, bounded record reads, CreateNew initial claim and flushed atomic replacement. It is not a cryptographic trust store, distributed lock, backup/restore protocol or protection against a malicious local writer able to replace its directory. Rollback/deletion of the journal could erase replay protection; production adoption requires a durable independent authorization/ledger claim and an approved private storage/backup lifecycle. Do not place journals in ordinary logs, support exports, public staging or generated-media directories. No existing schema or installed data is changed by this checkpoint.
