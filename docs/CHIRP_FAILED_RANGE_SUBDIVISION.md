# Lossless subdivision of one failed Chirp request

Google can report that sentences are too long even when a request fits its input-byte limit. No numerical sentence threshold is assumed here, and smaller requests are not guaranteed to succeed.

The offline clause proposal splits only one failed original request at punctuation and line breaks already present in the source. It preserves every Unicode scalar, space, quote and line ending. It does not add punctuation, rewrite the article, change the voice, call Google, approve spending or alter a stored plan.

A refined article is a new immutable plan. It embeds its exact original predecessor and pins the consumed terminal HTTP400 invalid-argument attempt, queue state and local attempt identifier. All other unaccepted requests retain their original payloads. Accepted predecessor ranges are reused as whole ranges from their original receipts; they are not copied, reimported or generated again.

Production verification requires the native source revision, complete financial baseline, original plan, terminal failed outcome, accepted queue states, final receipts, output journals, saved media hashes and any catalog-resume execution mapping. A provider success without its completed local receipt blocks refinement until local recovery finishes. Unknown or in-flight outcomes also block it. Historical reservations remain counted regardless of whether an actual charge has been confirmed.

The existing one-request review, reservation, durable dispatch barrier, accepted-output storage and FFmpeg article export remain the execution path. There is no new synthesis loop. The new plan is appended transactionally with its first reservation. An original plan and one exact refined child have one unambiguous export leaf; siblings, orphans, nested refinements and changed parent metadata fail closed. Existing plan and receipt bytes remain unchanged.

Original native-child audio and internal Chirp audio use separate provenance checks. Internal reuse names the original plan and authorization, and reads the existing receipt and media from their verified local locations. All accepted predecessor receipts must be reused exactly once. A derived historical association may be appended for the new plan only with the same source, queue, spend record and retained amount; the old association remains pinned and unchanged. This adds no reservation or credit.

## Admission and release requirements

An offline proposal is not authority. A changed request needs independently reviewed admission and explicit bounded authorization replacing any earlier first-failure stop. A pilot policy should allow only one exact new request. Only its verified accepted outcome can unlock the separately reviewed remainder; neither a caller-provided success flag nor the existence of an MP3 is sufficient.

An active completion register remains bound to its original manifest, build and fixed window. Refinement does not reset or extend it. A new run requires a supported independently reviewed successor-run transition which preserves the old register, counters, receipts and all financial holds. Until that transition, exact release checks and native acceptance pass, the refined plan must remain offline.

Private response capture remains off unless separately and explicitly authorized. Routine diagnostics retain safe status and reason categories, not article contents or raw provider messages. Final delivery still requires complete ordered source coverage, two continuous MP3 exports, full decoding and audible checks of starts, ends and joins. Decoder success alone does not verify spoken content.
