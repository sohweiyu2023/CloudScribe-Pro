CloudScribe Pro 1.0.1 - Building the Windows executable
=========================================================

QUICK DEVELOPMENT BUILD
--------------
Double-click:

    BUILD-CLOUDSCRIBE-WINDOWS.cmd

or run it from Command Prompt / PowerShell while you are in the extracted
source folder.

The launcher checks for the required .NET SDK, restores the locked dependency
graph, builds CloudScribe.App in Release configuration, publishes a runnable
Windows folder, verifies the expected runtime files, and opens the output folder.

Prerequisites: Windows, exact .NET SDK 10.0.402 selected by global.json,
PowerShell 7 (pwsh), and Python 3 on PATH. A newer SDK alone is insufficient
because rollForward is disabled. The launcher builds the app only; it does not
run the solution test suite or certify a release.

The launcher removes an existing sibling CloudScribe-Windows output folder.
Keep personal files and working installations elsewhere. To preserve an existing
output, use the manual commands below with a new empty destination.

The runnable output is created as a sibling of the source folder:

    ..\CloudScribe-Windows\CloudScribe.exe
    ..\CloudScribe-Windows\RUN-CLOUDSCRIBE.cmd

WHICH PROJECT IS THE APPLICATION?
---------------------------------
The executable desktop project is:

    src\CloudScribe.App\CloudScribe.App.csproj

CloudScribe.Domain, CloudScribe.Application, CloudScribe.Infrastructure and
CloudScribe.Providers.Abstractions are library projects, so DLL output from those
projects is expected.

Visual Studio / dotnet build may print a line ending in CloudScribe.dll for the
CloudScribe.App project. That build message identifies the managed assembly; the
Windows apphost CloudScribe.exe is also expected in the app output when the
project is built normally.

Typical Release build output:

    src\CloudScribe.App\bin\Release\net10.0\CloudScribe.exe

For the clean runnable handoff folder, use BUILD-CLOUDSCRIBE-WINDOWS.cmd rather
than copying individual files out of bin\Release.

WHY THE LAUNCHER USES -ExecutionPolicy Bypass
----------------------------------------------
Windows can mark scripts extracted from an Internet-downloaded ZIP as originating
from the Internet. Under RemoteSigned, an unsigned downloaded .ps1 can then be
blocked even though the source itself is valid. The launcher invokes the reviewed
repository publish script in a child PowerShell process with:

    -ExecutionPolicy Bypass

This is process-scoped only; it does not change your persistent PowerShell
execution-policy settings.

If a managed MachinePolicy or UserPolicy requires signed scripts, that Group
Policy has higher precedence and the process-scoped override will not defeat it.
Inspect the effective scopes with:

    pwsh -NoProfile -Command "Get-ExecutionPolicy -List"

Do not weaken an organization-managed Group Policy. Use the administrator's
approved/signed-script path instead.


PATH NAMES WITH PARENTHESES / REPEATED DOWNLOADS
-------------------------------------------------
The launcher is designed to work when the extracted source is inside an ordinary
Windows Downloads folder whose name contains parentheses, for example:

    CloudScribe-Pro-source(7)

You should not need to rename the extracted folder just to build CloudScribe.
The launcher deliberately avoids CMD parenthesized command blocks around paths
derived from the source directory and keeps delayed expansion disabled so common
path characters such as parentheses and literal exclamation marks are preserved.

MANUAL BUILD AND VALIDATION
-------------------------------
From the extracted source root:

    dotnet restore CloudScribe.sln --locked-mode --disable-parallel --configfile NuGet.config
    dotnet format CloudScribe.sln --no-restore --verify-no-changes
    dotnet build CloudScribe.sln -c Release --no-restore --disable-build-servers -m:1 -nodeReuse:false -p:BuildInParallel=false -p:UseSharedCompilation=false
    dotnet test --solution CloudScribe.sln -c Release --no-build --no-restore

Run source and verifier checks separately:

    python -B tools/update_sha256_manifest.py --check
    python -B tools/verify_repository.py
    python -B tools/verify_exact_v222_controls.py
    python -B tools/verify_project_dependencies.py
    python -B tools/verify_stage1_source.py
    python -B tools/verify_stage2_source.py
    python -B tools/run_python_regression_shards.py --all
    python -B tools/run_verifier_self_tests.py

The self-test runner projects a temporary historical Stage4 fixture for its
Stage4 contracts. Standalone Stage3/Stage4 verifiers expect their historical
stage/SDK identities and do not accept the current Stage8/app-1.0.1 tree.
After intentional source/doc edits, regenerate SHA256SUMS.txt with
python tools/update_sha256_manifest.py, then rerun --check. Inspect unexpected
changes before refreshing. Keep evidence, archives and backups outside the repo.
Build outputs in bin/obj are excluded by the manifest tool.

The repository publish script can then be invoked in a one-off child process:

    pwsh -NoProfile -ExecutionPolicy Bypass -File .\scripts\publish-stage2-windows.ps1 -OutputDirectory "<new empty absolute sibling output path>" -Configuration Release -Status verification-pending

The script retains its historical stage2 name and governance marker; it publishes
the current built app. It requires an empty physical destination outside the
source tree. See docs/SHARING_WINDOWS.md for portable private-runtime packages
and docs/WINDOWS_INSTALLATION.md for permanent installation and updates.

IMPORTANT
---------
A successful build/test run does not certify runtime behavior or promote a
release. Preserve active certification workflows and manual Windows acceptance.
SESSION_STATE.json retains historical Stage8 1.0.0 governance while the app is
1.0.1; do not rewrite the historical stage identity to match the application.
Historical batch records remain verifier inputs. Superseded handovers and unused
transport fragments are recoverable from Git history and the external backup.
Chirp internal article integration additionally uses synthetic admission parser/outer-entry tests:
  pwsh -NoProfile -File scripts/Test-RecoveryAdmissionPolicy-SelfTests.ps1
  pwsh -NoProfile -File scripts/Test-ChirpArticlePolicy-SelfTests.ps1
These checks do not install, admit live authority or submit provider requests. Full local tests use
synthetic profiles/fake providers; production/native and paid acceptance remain separate gates.
